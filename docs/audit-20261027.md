### N1 股本稀释率方向颠倒

- 错在哪：`rebuild_financial_summaries` 里 `reports.sort(key=report_date)` 是**升序**（`:979`），故 `shares_vals_5[-1]` 是最新、`[0]` 是最早；而 `:1029-1030` 把 `earliest` 赋给 `[-1]`、`latest` 赋给 `[0]`。同函数 `ocf_latest = ocf_vals_5[-1]`（`:1016`）与 `debt_ratio_latest = reports[-1]`（`:1056`）用的是正确约定，可作旁证。
- 后果：5 年扩股 50% 算出 `-50` → 门规 9 `dilution > 20`（`value_screener.py:344`）放行；持续回购缩股算出正数 → 被误杀。**两个方向都错**，且 `share_dilution_10y` 同病。
- 修法：两行对调（`earliest = vals[0]` / `latest = vals[-1]`），5y 与 10y 各一处。
- 完成标准：扩股样本得正数、回购样本得负数；门规 9 对扩股样本返回 `[]`。
- 验证：`bash scripts/gate.sh`（生产）+ 生产抽一只有送转的票核对符号。
- 测试归属：`tests/collector/test_financial_summary_20261026.py`（已调 `rebuild_financial_summaries`，补稀释方向断言）。AGENTS.md：`collector/` 改动必须附单测。

### N2 舆情日报正文看不到新闻

- 错在哪：`+` 比 `or` 结合更紧，`"..." + NL + NL.join([...]) or "- （无）" + ... + block + "要求 1-5"` 整条左侧（开头提示词必非空）为真 → 右侧**全部丢弃**，`【新闻条目】`块与 5 条写作要求从不进入 prompt。
- 后果：模型只凭一行 `overall` 自由发挥写日报；`digest` 看着正常，实际与新闻内容脱钩——属于「静默错答」，比崩更危险。
- 修法：`(NL.join([...]) or "- （无）")` 加括号，其余拼接保持在 `or` 之外。
- 完成标准：`body_prompt` 同时包含 `【新闻条目】`、block 首行、`5. 日期写`。
- 验证：单测直接断言 prompt 子串；无需真实 LLM。
- 测试归属：`tests/news/test_news_feature.py`（现有用例只断言返回值，未覆盖 prompt 内容）。

### N3 质量门异常值单位错

- 错在哪：`excess_20` 落库单位是**百分点**（`database.py:401` 注释「个股 - 基准（百分点）」；`tests/analyzer/test_outcomes.py:151` 造的即 `5.0`/`-2.0`），而 `quality.py:167` 用 `ABS(excess_20) > 1.0`。
- 后果：任何超额 >1pp 的行都算异常值；`outliers_max = 0`（`quality.py:36`）→ `evaluate` 判 invalid → 以 `analysis_outcome` 为数据集的实验**全部被质量门杀掉**（不报错，只是永远 invalid）。
- 修法：阈值改 `> 100`（即 100pp），并把单位写进注释；阈值宜提到 `_THRESHOLDS` 里可配。
- 完成标准：`excess_20 = 5.0` 不算异常、`excess_20 = 400` 算异常。
- 注意：`tests/research/test_quality.py` 用小数（0.005/1.5）播种，把错误单位固化进了测试，**改代码必须同时把测试改成百分点口径**，否则测试会反向锁死 bug。
- 测试归属：`tests/research/test_quality.py`。

### N4 regime 广度阈值与生产者量纲不一致

- 错在哪：`market_state.py:270` 输出 `round(100.0 * above60 / total, 4)`，字段注册表把 `pct_above_ma60` 的单位声明为 `%`（`:92-93`）；`regime.py:66` 阈值却是 `0.6 / 0.4`。
- 后果：`evaluate_rule`（`regime.py:94-95`）里 `value >= 0.6` 只要有 0.6% 的股票站上 MA60 就 +1 → trend 规则事实上恒判看多，regime 与 confidence 长期虚高。
- 修法：把 `default_rules` 的 trend 阈值改 60/40（与 `%` 声明一致），`value_vs_growth` 一并按其真实单位复核。
- 完成标准：真实向量（0–100）与规则阈值同量纲； breadth 35% 时 trend 不再给 +1。
- 注意：`tests/research/test_regime.py:22,32,44,51` 手工喂 0.8/0.2 等小数，**契约从未被测到**；改阈值必须同步把这些夹具改成生产者口径，并新增一条「用 `compute_market_state` 真实输出跑 `classify_regime`」的端到端用例，否则同类漂移还会发生。
- 测试归属：`tests/research/test_regime.py`。

### N5 OCF/NI 精确门永远不执行

- 连带：`net_profit_5y_sum` 被**硬编码写 None**（`akshare_fetcher.py:1057`）；即便列补齐，`:214` 用 5 年累计 OCF 除以单年净利（≈5 倍虚高），`:217` 把「元」除以「净利率% × 1e8」（量纲不成立）。

### N6 `close_qfq` 无写入方 + `close` 口径混装

- 证据：`KlineDAO.upsert_many` 的 INSERT/ON CONFLICT 列清单（`database.py:1461-1483`）不含 `close_qfq`；全仓唯一写它的是**一次性脚本** `UPDATE kline_daily SET close_qfq = close`（`fix_price_contract.py:48`）。列本身由 `database.py:515` 的 ALTER 添加。
- 更严重的第二层：`fetch_kline_data(adjust="qfq")`（`:1216`）东财分支按 qfq 取价写入 `close`，而腾讯兜底分支 `_fetch_kline_tx(code, start_str, end_str)`（调用 `:1248`，定义 `:1283`）**没有 adjust 形参**，返回不复权价，同样落到 `close`。调用方不感知降级。
- 后果：① 脚本之后新增的每行 `close_qfq` 都是 NULL，`docs/architecture.md` §9 的子项目契约「close_qfq 非空」在无声中破口，paper_trading 侧只能拿到 NULL 或旧值；② 东财限流当天抓的那些行是另一套价，`close`（以及由它回填的 `close_qfq`）在同一只票里存在台阶——`excess`/MOS/回测全被污染。已知 push2his「约 35 次快速请求后拒连」是常态，所以这不是理论风险。
- 修法建议：① `upsert_many` 接受并写 `close_qfq`（`COALESCE(excluded.close_qfq, close_qfq)`），保持与 `close_raw/close_adj` 同样的「旧调用不清空」纪律；② 腾讯分支显式标注口径，把 raw 写进 `close_raw` 而非冒充 qfq 进 `close`，或在返回记录里带 `adjust` 标记由调用方拒绝混写。**②属于口径决策，需要用户拍板，不宜由修 bug 顺带改掉。**
- 完成标准：`SELECT COUNT(*) FROM kline_daily WHERE close_qfq IS NULL` 在最近一天为 0；单日源降级不会改变 `close` 口径。
- 测试归属：`tests/models/test_kline_daily.py`、`tests/research/test_price_contract.py`。

### N7 `_mos_at_entry` 前视

- 错在哪：函数 docstring 自陈 PIT 规则「用 notice_date <= 分析日 的最新年报」（`outcome_service.py:67`），实现却是 `nd = r.get("notice_date") or r.get("report_date")`（`:74`）。年报 `notice_date` 缺失时（handoff 记 `notice_date` 覆盖约 51%，10-26 清单 D6 记 3%——**两处口径不一致，修复前先在生产确认**）退化成「12-31 即已知」，而实际披露在次年 1–4 月。
- **这不是口径争议，是违反仓内已落档的明文规则**：`valuation_percentile.py:7-8` 写着「**没有 notice_date 的年报不参与**（不回退 `report_date`——会计年末与实际披露差约 3 个月，回退即前视）」，且该文件头部记了「2026-10-25 修前视与股本口径」。同一类前视在估值分位已修过一次，`outcome_service` 这条是同族漏修，修法照抄估值分位的既有口径即可，无需产品决策。
- 后果：入场时点上用了尚未公布的年报 → MOS 系统性偏乐观。P0-9 研究恰好以 MOS 分层，等于用前视变量做分组。
- 修法：去掉 `report_date` 兜底，`notice_date` 为空即视为不可用返回 None（fail-closed，与仓内既有口径一致）。
- 完成标准：无 `notice_date` 的样本得 `mos_at_entry = NULL` 而非数值。
- 副作用要如实披露：改为 fail-closed 后 `mos_at_entry` 覆盖率下降，依赖它的实验样本量变小——这是正确性换来的代价，不是回归。
- 测试归属：`tests/analyzer/test_outcome_mos_p0_20261023.py`（现有用例只播种了带 `notice_date` 的行，需补 NULL 分支）。

### N8 `pe_ttm_max` 查的是静态 PE

- 错在哪：`value_screener.py:75` `('pe_ttm_max', _num('pe'), 'le', 'PE_TTM')`；`pe_ttm` 只在采集期临时存在（`akshare_fetcher.py:286`、`:358-366` 已折进 `pe`），`stock_snapshot` 无该列（`database.py` 全文无 `pe_ttm`）。
- 后果：三条策略配了 TTM 上限（`strategies.yaml:22`=60 / `:34`=22 / `:48`=18），实际执行的是「静态 PE ≤ TTM 上限」。静态 PE 通常低于 TTM PE（亏损转盈的票差距更大）→ 红利池/困境反转池放进本该被 TTM 天花板拦掉的标的。
- 修法二选一（**属口径决策**）：① 采集期把 `pe_ttm` 落列（ALTER + 快照写列）后改 `_num('pe_ttm', 'pe')`；② 删除 `pe_ttm_max` 配置键，别保留一个名不符实的闸门。
- 完成标准：闸门比较的指标与键名一致，或键不存在。
- 测试归属：`tests/screener/test_value_screener.py` + `tests/test_strategies_config.py`。

- **N12**：`status="running"` 已在 `:143` 落定，`_execute` 的 import 与 `task["total"]` 取值在 `try`（`:156`）之前，而 `_loop` 对 `_execute` 无兜底（`:150`）→ 一次异常就让 `ai-queue` 线程静默死亡：`_loop` 只挑 `queued`，队列彻底停摆，UI 与 `pipeline_progress` 永远显示运行中。修法：把取数移进 `try`，并给 `_loop` 外层加「异常落 failed + 记日志 + 循环不退出」。
- **N13**：唯一退出条件是 `instrument_id IS NULL` 计数归零（`:31`），但 `'CN:' || code` 在 `code` 为 NULL 时结果仍是 NULL（SQLite 拼接语义）→ 永远退不出，每轮 2 万行 UPDATE 事务反复抢写锁，饿死 Web 写入。加 `AND code IS NOT NULL` 与 `rowcount == 0` 兜底。生产当前 NULL 为 0（handoff 记 0/2,150,145），属**潜伏雷**。
- **N14**：`_floor()` = `tr -dc '0-9' < 基线文件`。现在两个基线文件恰好只有裸数字（`856` / `242`）所以没炸；一旦有人给它加一行日期注释，下限变成 `20261027856`，此后每次部署 fail-closed，且失败信息会让人误判是测试挂了。改成只取首个数字行。另 `:21` 的 `rm -rf "${LOCALAPPDATA:-/tmp}"/pytest-gate-*` 会删掉**并发**门禁的 basetemp（互踩致偶发 ERROR），应只删自己 PID 的那个。
- **N15**：`return dict(_config_cache)` 后那句注释「防止外部修改」只对顶层成立；调度器、AI 队列、Web 三条线程共用同一份嵌套配置，任何一处 `cfg["ai"]["x"]=...` 都会改到全进程。改 `copy.deepcopy`（在锁内）。
- **N16**：`record_result` 做 `st['ok'] += 1`（`ai_analyzer.py:707-716`）、`mark_dead` 写 `self._dead`（`:693-700`），而 `analyze_batch_parallel` 用 `ThreadPoolExecutor(max_workers=workers)`（`ai_queue.py:76-77`，并发数来自 `_workers_now()`，见 `:158`）+ 复盘/新闻线程并存 → 读-改-写丢计数，且 `_alive()`（`:669`）遍历字典时可能撞上并发改 `self._dead` 抛 `RuntimeError`。实测 `grep -c "_lock" src/analyzer/ai_analyzer.py` = **0**（该文件无任何锁；`ai_queue.py:71` 的 `with lock:` 只护队列自己的计数，不护 pool）。修法：`FreeModelPool` 内加一把 `threading.Lock` 包住 `_stats`/`_dead`/`_pool`。
- **N17**：`ci_low=metric_stats.get("ci_low") or 0.0`、`ci_high=... or 0.0`（`:287-288`）把「没算出 CI」写成零宽区间；`p_value: float = 0.0`（`domain.py:297`）默认即「极显著」。落库后两者都读起来像最强的结论。修法：缺失存 NULL，且 `p_value` 无值不给默认。
- **N18**：`step = rebalance_days`（默认 21，`:450`）驱动 `for i in range(0, len(dates), step)`，窗口是 `[i+1, i+1+horizon]`（`:466-468`）；`:451` 只校验 `>=1`。当 `horizon_days > rebalance_days` 时相邻窗口重叠，而 `:495-497` 仍按 `total *= (1+ret)` 复利累乘 → 累计收益被放大。修法：加 `step >= horizon` 校验，或改成非重叠链式持有。
- **N19**：`add()` 的列清单（`ai_watchlist.py:41-45`）不含 `monitor_condition`（该列由 `database.py:471` ALTER 加入）。`INSERT OR REPLACE` 会先删行再插 → 重新钉选一只票会**静默清空用户/AI 设的监控条件**。docstring 只声明「重置为 core、理由清空」，没说要清监控条件，故判定为 bug 而非设计。修法：改 `ON CONFLICT(code) DO UPDATE SET` 只写要重置的字段。现有 `tests/models/test_monitor_condition.py` 三条用例（`:29`、`:40`、`:53`）都是**先 `add` 再设条件**，没有覆盖「设完条件后重新 add」的重纳路径，所以本 bug 恰好落在测试盲区。补一条 `add → update_monitor_condition → add → 断言条件仍在`。
- **N20**：`rebuild_financial_summaries(stocks)` 的 `stocks` 参数从未被使用（`:949-960` 直接 `get_all_annual()` 后遍历全市场），而 `onboard.py:100` 传的是 `[{"code": code}]`、`_run` 又跑在 daemon 线程里（`:65`）→ 钉选一只股票触发全市场 summary 重写，与后台回填抢写锁。修法：按传入 codes 过滤 `by_code`。`tests/collector/test_financial_summary_20261026.py:31` 正好传单只，可加一条「只写入了这一只」的断言。
