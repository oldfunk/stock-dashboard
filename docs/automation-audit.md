# Stock Dashboard — 流程自动化审计

> 创建：2026-10-22 · 上游：三方审计意见 + 本仓实况核查 · 状态：现行（实施清单逐项推进，完成项回填 commit）

## 1. 判定标准与边界

三方审计给的判定口径（本文件沿用）：

- **该自动化**：重复发生、有客观成功/失败判据、失败后果严重（静默退化、部署不一致、基线倒退）。
- **不该自动化**：需要人的判断、自动化会掩盖问题、或会给设备增加常驻定时任务。

硬约束（本审计全程遵守）：不新增任何定时看门狗/巡检/新鲜度检查，不往用户设备加 cron 或 systemd timer；门禁基线只升不降；collector/screener/analyzer 不动或改动必附单测；禁删 S1–S8；`paper_trading/` 内不改；零 emoji。

核查中发现的实况修正（三方审计描述与本仓现状的差异）：

1. 基线数字当前并无漂移（AGENTS/architecture/iteration-log/README 均为 768，2026-10-22），但确实全靠人工逐处抄写，属"尚未出事的隐患"。
2. `deploy.local.md` 记录的部署目标 `pi1`（192.168.50.210）已不可达，实际生产主机为 ssh 别名 `pi`（192.168.50.60）——人工维护配置漂移已实证，本次顺手修正（该文件不入库）。
3. 生产侧自动化程度比审计假设的高：纸盘 tick、交易日历同步已在生产 crontab；母侧 15:30 流水线在内置 scheduler。真正全手工的是**合并-部署链路**。

## 2. 人工步骤盘点表

| 步骤 | 现在怎么做 | 出错时会发生什么 | 该不该自动化 | 理由 |
|---|---|---|---|---|
| 合并前门禁 | 生产服务器手工跑 `bash scripts/gate.sh`，合并前无任何自动检查 | 坏代码合入 main，部署后才发现；或忘跑 gate 带病上线 | 该（并入一键部署脚本） | 客观判据（exit code）；由部署脚本强制前置，独立 CI 与 09-29 决策冲突，已拍板不上（见 §5） |
| 合并 main + 推送 nightly/main | 手工 git 命令序列（fetch/rebase/push/merge/push） | 漏推 nightly 无留痕；基于旧 main 合并产生分叉；push 错分支 | 该（一键部署脚本） | 高频、纯机械、判据客观（祖先关系检查 + push 结果） |
| 部署同步（pull + gate + 重启 + 健康确认） | 手工 ssh 四步 | 漏重启（新路由不生效——09-22 P0-1 真实发生过）；漏 gate；健康不确认 | 该（一键部署脚本） | 每次迭代必做；失败后果严重；判据客观（exit code / HTTP 200 / is-active） |
| 冒烟 import 检查 | 手工 ssh 单条命令 | 忘做，上线后 import 错 | 并入部署脚本（不单独立项） | 独立价值低，并入成本约等于零 |
| 基线数字记录 | 手工抄 gate 输出进 commit message 与四处文档 | 抄错/漏更新（尚未出事，但五处文档全靠人工同步） | 该（gate 下限文件 + 脚本输出可粘贴行） | 纯机械转录；"只升不降"规则现仅靠人脑执行 |
| vendor 子项目更新 | 手工 `git subtree pull --prefix=paper_trading paper-upstream <tag> --squash` | 拉错版本；漏 commit | 不该（本次不推进） | 已是单条命令；tag 选择与三表契约预审需人判断；"包工头指定版本"例外流程会被脚本碍事 |
| handoff.md / iteration-log.md 更新 | agent 收工手工撰写 | 下一班断档、历史丢失 | 不该 | 内容需判断；自动化撰写会掩盖问题（审计标准第 3 条） |
| 部署目标信息维护 | deploy.local.md 手工维护 | 目标漂移（已实证：pi1/192.168.50.210 失效） | 不该自动化，但改为被脚本读取 | 频率低；脚本读取后只需维护一处，漂移会立刻报错暴露 |
| 远端旧 nightly 分支清理 | 手工删 | 分支堆积，无害 | 不该 | 低频低害；删错有损失风险，收益不抵风险 |
| Discord 简报 | agent 手工推 | 漏推，无实质损失 | 不该 | 摘要内容需判断 |
| Release / tag | 手工打（有份量批次才打） | 漏打无实质损失 | 不该 | 发布节奏是判断题 |
| 纸盘 tick / 日历同步 | 已在生产 crontab（2026-09-30 起） | — | 已自动化，无需动 | 注意硬约束：不得再往设备加定时任务 |
| 母侧 15:30 流水线 / 周复盘 | 内置 scheduler daemon | — | 已自动化，无需动 | 同上 |
| scheduled-tasks.md 三类巡检报告 | 设计稿，从未实施 | — | 不该（不实施） | 实施即"定时巡检"，被硬约束直接禁止；服务健康由部署脚本健康检查 + 人工观察覆盖 |
| legacy 兜底脚本（daily_cron.sh / ai_analysis_cron.sh / daily_update.sh） | 仓库留存，生产 crontab 未引用 | 误安装触发已停用的本地 AI 全量触发；与内置 scheduler 双路径混淆 | 该清理（去自动化，非加自动化） | 死脚本是自动化结构负债；其中 daily_update.sh 还含 emoji，违反零 emoji 硬规则 |
| 上游新 tag 监控（paper-upstream） | 人工发现 | 漏跟一个 tag，无害（协议不承诺跟进时效） | 不该 | 节奏由包工头定 |

## 3. 实施清单（按收益/成本排序）

### P1 一键部署脚本 `scripts/deploy.sh`（已落地，2026-10-22 当日经用户拍板重启并实施）

- **预期收益**：拦住四类真实故障——(1) 漏重启导致新代码不生效（09-22 已发生）；(2) 合并前忘跑 gate 带病上线；(3) 基于过期 main 合并/漏推 nightly 无留痕；(4) 部署后不做健康确认。同时把"合并前门禁"从可选动作变成强制前置：gate 在生产 worktree 上先跑、绿了才允许合并 main，main 永远不含未验证代码。
- **实施成本**：新增 `scripts/deploy.sh`；`deploy.local.md`（本地配置，不入库）改 KEY=VALUE 块供脚本读取；AGENTS.md 收尾流程段补一行指针。不改任何 `src/`，不动 CI（`gate-baseline.txt` 属 P2，不在本项）。
- **风险**：不触碰硬约束——本机仍不跑 pytest（gate 在生产 worktree 执行）；不新增定时任务（脚本只由人触发）；不碰 collector/screener/analyzer/S1–S8/`paper_trading/`。生产侧新增一个持久化验证 worktree（`VERIFY_DIR`，detached HEAD，可复用），失败时 main 与生产服务均未动，可安全重跑。

### P2 基线下限自动强制 `gate.sh` + 单一事实源（已落地，2026-10-22 当日经用户拍板重启并实施）

- **预期收益**：把"基线只升不降"从人脑记忆变成机器强制——删除/跳过测试导致通过数低于记录下限时，gate 直接失败，部署被 P1 脚本拦下。基线数字只在 `scripts/gate-baseline.txt` 一处维护，AGENTS/architecture/iteration-log 改为引用该文件，消除五处人工抄写。
- **实施成本**：改 `scripts/gate.sh`（约 15 行：捕获 pytest 输出、解析 passed 计数、比对下限文件）；新增 `scripts/gate-baseline.txt`（首值 768）；AGENTS.md / architecture.md §5.3 / iteration-log 顶部各改一行指向该文件。经 P1 脚本在生产 worktree 实测。
- **风险**：gate.sh 是全仓唯一门禁，改坏则全链路阻塞——因此必须先经 P1 的"生产 worktree 先行验证"跑绿才合并；不触碰其他硬约束。

### P3 legacy 死脚本清理（缓做：2026-10-22 三方审计收窄范围，本轮不实施）

- **预期收益**：消除三个"误触发即闯祸"的陷阱——`ai_analysis_cron.sh` 若被安装会触发已停用的本地 AI 全量分析；`daily_cron.sh` 头注释主动邀请装 crontab（与硬约束冲突）；`daily_update.sh` 含 emoji 违反硬规则。同时让 README 脚本表与现实一致。
- **实施成本**：删 3 个文件 + README 结构树与脚本表各删对应行。保留仍可手动使用的 `stock-ai-slow-feed.sh` / `run_pipeline.py` / `run_ai_analysis.py` / `retry_ai.py`（README 手动操作表在用）。
- **风险**：无——已核实生产 crontab 无任何引用；纯删除，不动运行时代码。

### P4 GitHub Actions CI（已落地，2026-10-22）

- 决策反转记录：本文件初稿维持 09-29 "母不上 CI"；同日三方审计补救提出"每次合并 main 前要有机器产生的测试记录"，用户拍板采纳（范围收窄为本轮唯一实施项）。
- 落地形态：`.github/workflows/gate.yml` 一个文件——`pull_request` + `push`（main）双触发，ubuntu / Python 3.13 / `TZ=Asia/Shanghai` 对齐生产，`pip install -e . pytest` 后原样调用 `scripts/gate.sh`（未改它）。无矩阵、无发布流水线、无打包。
- 能力边界如实声明（2026-10-22 二修，审计指正"休眠能力"表述）：本仓工作流是本地 ff 合并后直推 main，真实合并只有 push 触发——即"每次合并的机器记录"（事后记录）。"合并前"的机器验证由生产 worktree gate 承担（合并惯例，非 CI）；pull_request 触发仅在出现真实 PR（外部贡献）时激活，届时才产生 PR 侧"合并前"记录。权威门禁仍是生产 gate，开发/测试分离规则不变。
- 自证（红验证，方案 A）：一次性分支 `ci-verify-red` 加故意失败测试 → PR #2 → CI 红 **1 failed, 768 passed**（唯一失败即探针；768 与生产基线一致，旁证 CI 环境与生产对齐）→ 关 PR 删分支，main 零污染。证据：Actions run 39773737114。

## 4. 明确不自动化的项及理由（汇总）

1. **vendor subtree pull**：已是单条命令；tag 选择、三表契约预审、"包工头指定版本"例外都需要人的判断，脚本化反而碍事。
2. **handoff / 账本内容生成**：判断密集；自动化撰写会掩盖真实问题。
3. **Discord 简报**：同上。
4. **nightly 分支清理 / Release 打版**：低频，判断密集，删错/错发有损失。
5. **巡检报告类（scheduled-tasks.md 设计稿）**：实施即违反"不新增定时巡检"硬约束，且设计稿从未被需要过。
6. **看门狗/新鲜度检查/设备侧定时任务**：硬约束直接禁止。
7. **上游 tag 监控**：协议不承诺跟进时效，节奏由人定。
