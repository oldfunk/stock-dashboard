## F 表 — 成交缺口归因（收口 T9 §3.6）

```
rqalpha  信号 111 → 成交 108（流失 3）
旧引擎   信号 109 → 成交  80（流失 29）
旧引擎 skipped 分类计数: {'无可卖持仓': 15, '金额不足一手': 14}
```

- **14 笔「金额不足一手」**：规则里 `action.value = 100 × 窗口首根收盘价`。
  价格上穿窗口首价后，`size_for_value(price, value)` 向下取整到整手 ⇒ **0 手 ⇒ 买不进去**。
- **15 笔「无可卖持仓」**：上面那些漏买的票，死叉到来时自然无仓可卖 ⇒ 连带流失。
- 29 ≈ 108 − 80 = 28（差异来自 rqalpha 侧 3 笔自身流失与集合边界），**缺口已闭合归因**。
- ⚠️ 诚实边界：这是 **D2 股数语义配置**下的归因。T9 里那个"value=400×首价"变体仍有
  ~26 笔缺口未测原因（推测为现金/仓位上限开始生效），**不要把它当已解释项**。

## 我自己踩的坑（写进报告，供 harness 复用者避雷）

`history_bars()` 返回 **numpy 数组**，我第一版写成 `history_bars(...) or []` ⇒
`ValueError: truth value of an array ... is ambiguous`，而外层 `except Exception: continue`
把它**静默吞掉 1680 次**，跑出"0 成交、0 信号、退出码 0"。
⇒ 这与我们在 T17 里要修的缺陷是**同一类**（异常/流失被静默吃掉），
建议 parity/live-sim 的所有 harness 统一加一条断言：
**`handler_invocations > 0` 且 `signals > 0`，否则视同失败**（rqalpha 只会记
`策略运行产生异常`，run_func 仍返回成功）。
