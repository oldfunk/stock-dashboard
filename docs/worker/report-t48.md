# report-t48 · M3 新线执行模型方案对比（Qoder，P0·只出方案不改码）

分支 `worker/t48`（堆叠 `worker/t50`）。基线 `main@085e318` + T50。
**本文不写实现**，只把三个方案的四项代价量化到可以拍板的程度；
所有"开销"数字都是 **NEC 现网实测**（Core2 Duo T9900 / 38 只 × 3 年 raw），不是估的。

## 1. 实测基线（三方案共用的成本因子）

| 量 | 实测 | 怎么量的 |
|---|---|---|
| 一个 rqalpha 会话（38 只、3 年 raw、1 笔成交） | **2.42 s / 峰值 RSS 171 MB** | `rq day --today 2026-10-29`（NEC 引擎 venv，`/usr/bin/time`），`ok=True`、费用 9.7708 与手算一致 |
| 其中 `import rqalpha` 固定成本 | **0.83 s / 95 MB** | 同上，只 import |
| 同日第二次跑（复用 state） | **0.93 s 后被闸拒**，exit 4 | SessionGate 指纹/日期判重 |
| 无共享状态连跑 5 次 | 每次 **2.4 s**，**每次都成交 1000 股** ⇒ 净买入 5000 股 | E3：5 个独立 state 目录 |
| 一次双轨影子对账（两侧都跑） | 5 s（T39）/2 s（T40，库已热身） | `rq shadow-day` |
| 一次全池盘后采集（38 只 × 3 年） | 42 s（T50 实测） | `data fetch-raw --days 560` |

一句话：**每次会话的固定开销里约 1/3 是 Python 装载 rqalpha 本身**；
而"每分钟一跳"真正的障碍不是 CPU（2.4 s ≪ 60 s），是 **状态与幂等**。

## 2. 三方案对比

### 方案 ①：每分钟一个短窗口进程（`start=end=今日`，一天 240 跳）

- **止损延迟上界**：≤ 60 s + 会话耗时 2.4 s ≈ **1 分钟**（与旧线 `* 9-15` 每分钟一轮同级）。
- **state/账本一致性风险：高（这是它的致命处）**。T13 的取证说明 resume 只跳
  `before_trading`、`handle_bar` 会再执行一次（现网闸文案就是照此写的），
  所以"同一天再跑一次"必然重复下单——E3 实测 5 跳 = 5 倍仓位。
  要做成，必须新增三件今天不存在的东西：
  (i) **日内共享状态**：每跳从 persist 恢复"今天已下的单/已成的交/已用的额度"；
  (ii) **计划增量语义**：策略只补差额（已有 1000 股就不再造 1000 股），
  这会把"下单意图"从 cron 参数变成需要持久化的状态机；
  (iii) **幂等闸改写**：`SessionGate` 从"同日重跑即拒"改成"同日可续，但必须恢复成功"
  ——而 §4.7 明确 `should_resume/should_run_init` 在核心里**没有实现**（接口是死的），
  恢复路径只能我们自己做，做错的后果直接是重复成交。
  另外每跳都重放上一日 SETTLEMENT（§4.4）⇒ 一天 240 次重复结算，
  "退市/换代码/管理费"三类语义被放大 240 倍——T13 已警告不能当无害。
- **实施工作量：大**。约等于把 G1（写账本）+ 一套日内状态机 + 幂等重写一起做掉；
  粗估 3 个 P0 件的量（账本适配、日内状态、闸重写），且每一项都是钱类。
- **回退难度：低-中**。cron 换线即可回到旧线；但**中途状态**（当天已下单）
  需要人工核对，不能只回 cron。
- 结论：**不推荐作为第一期**。它的 CPU 代价其实最小（240×2.4 s ≈ 每天 10 分钟机时，
  盘中占比 ~4%），代价全在正确性上：一天 240 次"跨进程续跑"正好命中 T13 两个 P1 的放大版。

### 方案 ②：常驻长窗口进程（一天一进程，日内每分钟由 rqalpha 自己的调度驱动）

- **止损延迟上界**：取决于**能否让 rqalpha 在一天内产出分钟级 bar**。
  日线 bundle + `frequency="1d"` 下，`handle_bar` 一天只有一次 ⇒ 止损只能到收盘，
  这就是被否决的"两轮"同一条问题；要做到分钟级必须 `frequency="1m"` + 分钟线供数
  （我们有 `minute_bars`，T35 已把 period 进主键），
  于是**每分钟一跳变成"每分钟一根 bar 进同一个进程"**，延迟上界 = 分钟线延迟（≈1 分钟）+ 采集节奏。
- **state/账本一致性风险：中**。单进程内没有 §4.7 的重入掩盖问题（一天一会话），
  但**进程活一整天**意味着：崩了就丢当天未落盘的会话状态（要靠 `persist_mode=real_time`
  + 我们的 FilePersistProvider 原子写，T32 已建）；跨日续跑仍会撞上 §4.4 的重复结算
  （一天一次，不是 240 次，可控但仍需 `sys_analyser` 禁用，现已禁）。
  真正的风险是**账本写入时机**：常驻进程内下单→写库必须是"成交即落"，
  否则面板/AI 看到的是滞后状态。
- **实施工作量：中**。需要：分钟线适配器（`RawMinuteBarStore` + `frequency=1m`）、
  日内调度接我们自己的门禁（尺度闸/止损在 L2，框架不管）、G1/G2 账本件、
  进程守护（systemd/cron @reboot + 心跳，`m3 verify` 的 heartbeat 项已在盯）。
  工作量主要在"分钟线供数 + 门禁接线"，不在框架改造。
- **回退难度：中**。停常驻进程 + 换回旧 cron；账本状态是"当天到哪算哪"，
  与 ① 同样需要人工核对半日在途。
- 结论：**方向正确**（延迟与语义都能保住，状态只有一份、幂等天然成立），
  但依赖分钟线质量——我们的 `minute_bars` 目前只有 5 分钟周期、2,304 行、
  无长期回填与新鲜度闸（T35 只做了主键与管道），这是它的前置。

### 方案 ③：分层混合（盘中 L2 快路径判定 + 日终 rqalpha 结算/对账）

- **止损延迟上界**：**最低**——盘中判定仍由现有 `paper_trading.engine`（每分钟）执行，
  延迟与今天完全相同（≤60 s），不改任何交易节奏。
- **state/账本一致性风险：结构性风险最高**。rqalpha 在日终重放当天时，
  用的是它自己的撮合与状态；如果它得出与盘中已执行的成交不同的结果，
  就必须回答"以哪本为准"。两种答案都不干净：
  - 以盘中账本为准 ⇒ rqalpha 只是**重算/对账工具**，"框架是 L1 真相源"的目标没达到
    （数值红线：影响成交价/持仓/盈亏的数值必须来自框架返回值——这里没有）；
  - 以日终重放为准 ⇒ 一天里面板/AI 看到的账与最终账可能不一致（双账本风险，
    且盘中已下的单在真实市场里已经发生了，不能"改判"）。
  所以 ③ 能安全落地的唯一形态是：**rqalpha 只做影子对账（就是现在 M2 的形态）**，
  不做账本真相源。也就是说 ③ 其实不是"M3 切换方案"，而是"M2 延长线"。
- **实施工作量：小**（今天已经做到一半：`rq shadow-day` + 逐日留痕 + `m3 verify`）。
- **回退难度：最低**（盘中路径没换，切换失败就是把日终对账停掉）。
- 结论：作为**兜底/过渡**很有价值（尤其"如果 T47 的钱类件审不过来"时），
  但它不满足 M3 的定义，别把它当切换方案批。

## 3. 对比表（拍板用）

| 维度 | ① 每分钟短进程 | ② 常驻长窗口（分钟线） | ③ 分层混合（=M2 延长） |
|---|---|---|---|
| 止损延迟上界 | ≈1 分钟 | ≈1 分钟（依赖分钟线节奏） | 与今天相同（≤1 分钟） |
| 状态/账本一致性风险 | **高**：日内共享状态要新建，240× 重复结算，幂等闸需改写；做错=重复成交 | **中**：单进程一份状态；崩溃需靠实时 persist 恢复；跨日重复结算 1× | **低-中**：不改盘中；但**双账本口径**必须写死"以盘中为账、rqalpha 只判" |
| 是否达到"L1 数值来自框架" | 是 | 是 | **否**（框架不参与成交真相）→ 与 M3 定义冲突 |
| 实施工作量 | 大（≈ G1 + 日内状态机 + 闸重写，三件 P0） | 中（分钟线适配 + G1/G2 + 守护） | 小（已有 80%） |
| 回退难度 | 低-中 | 中 | 低 |
| 每日机时（实测外推） | 240 × 2.4 s ≈ **9.7 分钟** | 1 个进程全天（RSS 171 MB 常驻） | 1 × 日终 ≈ 5 s |
| 对 CPU 较弱的 NEC | 可接受（4% 盘中占用，但 240 次进程 churn + RSS 抖动） | 最省（一次装载） | 最省 |

## 4. 我的推荐（拍板参考，不是决定）

**②为目标形态，但第一期先交付 ①/② 共同的前置件**，顺序：

1. 先做 **G1 + G2（T47）**：账本写入器与 NAV 记录器——**这是 ①②③ 都需要的地基**，
   做完之后 ② 只是"把日内 bar 供进来"，① 只是"把闸改成可续"，都能接得上；
2. 同期把 **分钟线供数**当作 ② 的前置补齐（T35 的 minute_bars 现在只有 5 分钟、
   2,304 行、无每日采集与新鲜度闸 ⇒ ② 现在**跑不起来**，这是硬事实）；
3. **①不推荐**：它把 T13 的两个 P1 每天放大 240 倍，而换来的收益（延迟）②同样能给；
4. **③保留为兜底**：它的实际含义是"继续 M2 影子"，如果 T47 的钱类件过不了审，
   M3 就应该推迟，而不是用 ③ 冒充切换。
