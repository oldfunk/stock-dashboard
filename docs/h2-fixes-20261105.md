## 1. 四点怎么修的

| 编号 | 原错 | 现在的口径 |
| --- | --- | --- |
| P1-H2-1 | `_join_sector_size` 用 `ORDER BY snapshot_date DESC LIMIT 1`，不截日期 → 7 月的分析用 11 月的市值分档（前视），退市股在最新快照里根本没有行（幸存者偏差） | `AND snapshot_date <= 分析日`（与 `_block_snapshot`/事件研究一致）；取不到 → `size=None`、`sector=None` |
| P1-H2-1 附 | `(cap or 0) >= 1e10 … else "small"`：缺市值一路落到 `small`，把缺失算进"最容易出高收益"的桶 | 新函数 `_size_bucket(cap)`：`None/0/负 → None`，`>=1e10 large`、`>=1e9 mid`、其余 `small` |
| P1-H2-2 | `bucket.setdefault(str(r.get(key)), …)`：regime 缺失变成名为 `"None"` 的桶；分域只给均值 | `_bucket_label()`：缺值统一叫 `unknown`；每桶输出 `{"mean": …, "n": …}`；notes 里给分域覆盖率 `regime x/N、size x/N、sector x/N` |
| P2-H2-1 | `cutoff=(…).isoformat()` 后 `r["analysis_date"] <= cutoff` 整串比 → 带时间部分的行被分错侧（估计集/holdout 的分界决定预注册算不算数） | `_as_date()` 解析后按 `date` 比；**解析不了的行不静默消失**：留在估计集，并在 notes 计数（`N 行日期不可解析，留在估计集`） |
| P2-H2-2 | notes 写"样本 X 只股票 / 全市场 Y 只"，读起来像 X/Y 的覆盖率 | 改成"分析期出现 X 只股票；instrument 表当前 Y 只（**两者不是同一集合**…不能用 X/Y 当覆盖率）"，分母语义分开命名 |

每桶 `n` 放进 `splits` 里（`splits[维度][桶] = {mean, n}`），**没有新增 `splits_n` 字段**：
`ExperimentResult` 加字段要配 `research_result` 的列迁移，而 `splits_json` 现成；
均值与样本数分开两处存，迟早各自演化。旧用例 `set(splits["sector"]) == {"白酒","银行"}`
只看键，不受影响（`tests/research/test_outcome_study.py:135` 仍绿）。

**Hermes 建议里的"每桶 CI"这条我没做**，理由写在这里而不是默默跳过：
现在 bootstrap 调用次数 = horizons × tiers（默认 2×4=8 次，每次 `n_boot=1000`，
共 8 千轮重采样）；按桶再各跑一次是 8×(3 regime + 3 size + **76 sector**)=656 次
→ 65.6 万轮，80 倍，而多数桶 n 只有个位数（n=1 的 CI 是退化的 [x,x]，正是 N17 批评过的
"零宽区间读起来像精确到分位"）。需要桶内 CI 时用批15 的 `scripts/h001_regime_check.py`
离线算，不在每次实验里默认付这个钱。（76 = 产线 `stock_snapshot.sector` 去重值，只读实测）

## 2. 连带发现（第 5 处同类错）：取数窗口也按整串比

`_load_outcomes` / `_sole_benchmark` / `_notes` 三处 `analysis_date BETWEEN ? AND ?`
是**字符串**比较：`BETWEEN '2026-07-08' AND '2026-07-08'` 会把 `"2026-07-08 09:30"`
挡在单日窗口外——样本无声变少，而 notes 的分母用同一条 BETWEEN，两边一起错就没人发现。
既然要按日期分域、按日期切 holdout，取数窗口必须同一个口径，否则 `_join_regime` 的
截断修复在单日窗口下根本走不到（变成死代码）。三处统一为
`SUBSTR(analysis_date, 1, 10) BETWEEN ? AND ?`。

代价：放弃 `idx_analysis_outcome_date`（`src/models/database.py:424`），改成全表扫描。
产线该表 780 行，一次扫描远便宜于同一次实验里的 block bootstrap；即使按 5000 只 ×
250 天 × 2 基准 ≈ 250 万行的上限估，也只多几十毫秒级 IO，而实验本身跑分钟级。
`src/research/quality.py` 与 `src/web/data_api.py` 里还有同类字符串比较（
`analysis_date <= ?` / `>= ?`），**本批未动**：它们不在 H2 范围内，且 data_api 是
产线翻页查询、索引对它有意义——要不要统一，请母方裁定。

## 3. 生产只读实测：PIT 修好了，但**没有 PIT 源可用**

改完必须说清它把什么变坏了，否则只是把前视换成了沉默。
（`G:/qoder/probe_snapshot_pit.py`、`G:/qoder/probe_pit_source.py`，
`file:/home/nec/…/stock_dashboard.db?mode=ro` + `query_only`，2026-11-05）

```
stock_snapshot      rows=5527  codes=5527  每码行数分布={1: 5527}  snapshot_date 去重=51
analysis_outcome    rows=780   stocks=31   days=26  2026-07-08..2026-09-29
                    analysis_date 带时间部分的行数 = 0
旧口径（取最新一行）  命中 780/780
PIT 口径（<=分析日）  命中   2/780      ← 被挡掉的是 30/31 只股票

    risk_off 412 / neutral 342 / risk_on 22 / 无标签 4

候选历史源           stock_feature_daily=0 行、universe_membership=0 行、
                    daily_close 只有 4 天（10-30..11-04）、
                    stock_analysis_history 627 行但只有 score/ai_analysis（无 sector/市值）
```

结论三条，写给母方：

1. **`stock_snapshot` 一码一行**（`code` PRIMARY KEY + `save_batch` 用
   `INSERT OR REPLACE`，`src/models/database.py:697-727`）——51 个不同的 snapshot_date
   只是"各只票最后更新日不同"的残余，不是历史。所以旧实现的 780/780 命中不是覆盖好，
   是 30/31 只股票全被贴了**分析日之后**的行业/市值。
2. regime 维度不受影响（`market_state_daily` 本身按日存，776/780），所以 H-001 类
   "risk_off 暴露"复核仍然可跑；死掉的是 sector/size 两个维度。
3. 目前**没有**任何表能提供历史市值/行业。`sector`/`size` 分域因此在补源之前只能读
   `unknown`——这是"不再拿未来数据装现在的结论"的代价，不是回归。
   notes 会在覆盖率不满时明说（`…该表一码一行…分域可用度受快照历史限制，不是样本本身的问题`）。

**提请母方裁定（跨域，本批不动 models/collector）**，三选一即可：
- (A) `stock_snapshot` 改按日追加（去掉 `code` 单列主键，改 `(code, snapshot_date)` 唯一）；
  代价是详情页/搜索等按 code 取最新行的读法要一起改。
- (B) 不动主表，新增 `stock_snapshot_daily(code, snapshot_date, sector, market_cap, …)`
  由每日快照顺带写；读侧 `_join_sector_size` 只需换表名，PIT 立即生效。
- (C) 用 `financial_history.total_shares`（按 `notice_date` 可 PIT）× `kline_daily.close_raw`
  重建历史市值——不新增表，但口径是**估算**（股本仅按年报/季报披露，回购/增发滞后），
  行业维度仍然没有 PIT 源。

我倾向 (B)：改动面最小、不动既有读法、且 sector 也能一起有历史。
