# 事故复盘：2026-11-18 全天零成交（`rq:fill` 幂等键缺业务日）

> 结论先行：**一笔已经成交的单，被自己的幂等键当成了历史重放**。键里没有日期，
> 而"配置指纹"跨日恒定，于是 8 天后同标的、同数量的成交撞上了 11-12 的旧键，
> 落账静默跳过。账本没记、框架记了 ⇒ 期初对齐每跳拒绝开会话 ⇒ 当天一笔都没再成。
> 钱没多没少（账本自洽），丢的是一整天的执行能力和 6 条意图。

## 1. 事故概要

| 项 | 事实 |
|---|---|
| 时间 | 2026-11-18 09:32 首次会话；10:07 起全天拒开 |
| 首笔 | 框架成交 `BUY 100 000792.XSHE @21.88`（意图 `000792_BUY_100@2026-11-18T09:30:46`） |
| 落账 | `rq_tick.log:16581`：`{"biz_id": "rq-fill:34288a78d4b8736f:0:000792.XSHE:100", "why": "already_posted"}`，`posted: []` |
| 撞键源 | `op_log #513`（2026-11-12 16:54:19，reset 后重放）：同一 biz_id |
| 框架侧 | 现金 38,072.1624 → 35,879.14057；持仓 +100 股（`transaction_cost` 5.02188） |
| 账本侧 | 现金 38,072.1624 未动；当日 `fills` / `orders` 均无行；到收盘 000792 = 0 |
| 停摆 | `rq_tick.log:16880` 起 `InitPositionError: 框架账户比账本多 1 只仓`，当日 **142 次**，IdleSpin **142 次** |
| 结果 | 6 条意图积压（收盘仍 queued）、0 成交；15:30 daily-check **10 绿 / 5 黄 / 2 红**（`intent_queue`、`init_align`），`rollback_required=true` |
| 资金 | 20:50 `rq-nav` 记 `nav_history#37 = 95,807.1624`，账本现金/持仓自洽；无重复成交、无多付 |

## 2. 机理

```
09:32 会话（rqalpha）
  ├─ evidence.trades = [BUY 100 000792 @21.88]        ← 框架真成交了
  └─ cli.rq tick → ledger.post_session(today=2026-11-18, fp=34288a78d4b8736f)
        biz_id = rq-fill:{fp}:{i}:{symbol}:{volume}
               = rq-fill:34288a78d4b8736f:0:000792.XSHE:100
        _already_posted() 全表命中 op_log #513（11-12）
        ⇒ skipped[already_posted]，posted=[]，ok=true        ← 静默
10:07 下一跳：ledger_init_state 读账本（无 000792）
      session 恢复 state（有 000792 100）
      _check_positions_landed：framework 100 vs ledger 0 ⇒ InitPositionError
      ⇒ 每跳拒开会话，直到收盘
```

关键设计错误在两处叠加：

1. `fp`（`runner.session_fingerprint`）是**配置指纹**，不是会话标识——11-12
   `ledger reset-state` 重基线后一直是 `34288a78d4b8736f`，跨日不变；
2. `i` 只是**会话内**成交序号。`{fp}:{i}` 组合不含任何日期信息，历史越长，
   同标的同数量成交的碰撞概率越高（不是偶发，是必然）。

`post_session` 把"跳过"记为 `ok:true` 也放大了危害：调用方只看到成功，
账本/框架的口径差要等到下一跳的持仓对齐才暴露，而那时人已经不在屏幕前。

## 3. 为什么没有更早拦住

| 既有防线 | 为什么没响 |
|---|---|
| 幂等键 | 它**就是**故障点：跨日不可分辨，旧键把新成交判成自己 |
| `post_session` 守卫 | 费用分量齐全、幂等命中不是错误 ⇒ `ok:true`，无人报警 |
| `daily-check` 的 `intent_queue` / `init_align` | 只在 15:30 跑，收盘后才发现，且**当天已无可挽回** |
| `engine_crash`（11-17 新增） | 只扫 `engine.log` 里含 `crashed` 的行；本次拒开是 `rq_tick.log` 的 `InitPositionError`，关键词和文件都不在扫描范围 |
| 心跳 | tick 每跳都"跑完"了（退出码 0），心跳正常 ⇒ 看门狗认为链路活着 |

**教训**：幂等键必须由"业务事件身份"构成（业务日 + 会话/序号 + 标的 + 数量），
不能用"环境指纹 + 会话内序号"；而"跑了但什么也没做"必须变成可观测信号，
不能只看退出码。

## 4. 修复（`01f512f`）

两处最小 hunk，都不动 NAV 判据：

1. **`ledger.post_session`**：`biz_id` 加业务日
   （`rq-fill:{today}:{fp}:{i}:{symbol}:{volume}`）。带 `fp` 的路径不再查旧键
   （旧键跨日不可分辨，正是要修的）；无 `fp` 的路径保留旧键补判，同日重放仍去重。
2. **`cli` tick 写回**：`_q.mark(...)` 逐条循环 ⇒ `_q.apply_outcomes(...)`
   一次（内部 = `mark` + `_close_conditional` 同事务）。只 `mark` 会让条件单
   成交后永停 `queued_rq`（11-17 起 #94/#95/#104/#105/#106 的生产实况，T86 的另一半）。

回归测试 3 条，**都在未修复版本上实测红**：

- `test_post_session_same_shape_fill_on_later_day_is_posted_again`
- `test_post_session_without_fp_still_dedupes_the_legacy_key`
- `test_cli_tick_writeback_actually_goes_through_apply_outcomes`
  （直接读 `cli.py` 源码钉接线——把调用顺序抄进测试的写法对回退是免疫的）

账本 md5 前后核对；`op_log` 写 `ledger:reset-state` 留痕）。账本内容不变，
下一跳用 `ledger_init_state` 从账本重建框架账户。

  `live.pre-reset-20261119-004723`；

  外部复核双重核对，**逐项相同**：
